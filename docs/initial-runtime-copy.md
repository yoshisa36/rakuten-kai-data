# 初回データ複製CLI

## 状態と境界

このPRはCLI・人工テスト・文書だけを開発したものです。実際のdry-run取得や複製は実施していません。新側への書き込み、認証作成、本番保存先の切り替え、GAS・既存workflow・予約登録処理の変更は含みません。旧リポジトリを唯一の本番正本とし、自動返信OFFを維持します。

利用時の固定対象:

- コピー元 Public: `yoshisa36/rakuten-kai-data`
- コピー先 Private: `yoshisa36/rakuten-kai-runtime-data` のmain
- `threads-analysis.json`、`threads-queue.json`、`rakuten-affiliate.json`、`products.json`、`selection-history.json`、`batches/2026-10-05.json`

任意リポジトリ・任意パスの指定、双方向同期、削除、定期実行は実装していません。新側はREADME.mdのみを許可し、実行済みの同一計画を再検証する場合を除き既存JSONやmanifestがあれば停止します。

## 実行前の人間による確認

実データ取得・書き込みは開発テストと別の承認対象です。新側Private、main、READMEのみ、Actions無効、外部共同編集者なしを確認してください。CLIはPrivate・main・ファイル一覧・READMEを確認しますが、Actionsや共同編集者設定を管理権限で検査する機能は持ちません。

実行期間は他の主体による新側への書き込みを止めてください。旧側の更新や投稿は止めません。コピー元Sは固定コミットにするため、処理中に旧mainが進んでも複製に混ぜません。6ファイルが業務上の更新完了境界か、鮮度が十分かは別途判断します。

## 限定認証

新側リポジトリのみを選択し、Contents read/writeを付与した期限付きfine-grained PAT等を想定します。値は安全な実行環境で `RUNTIME_DATA_TOKEN` に設定し、コード・コマンド引数・URL・チャットに記載しません。このPRでは発行やSecrets登録を行いません。トークンの権限範囲自体をCLIが証明するわけではありません。

トークンは新側へのHTTPS要求にだけ添付し、公開のコピー元には添付しません。リダイレクトも拒否します。トークンはオブジェクト内に保持しますがログには出しません。CIには渡しません。GitHub FreeのPrivateリポジトリでブランチ保護が利用できるとは仮定せず、単独実行・限定認証・競合検出に依存します。新側Actionsは無効のままです。

## dry-run計画

次は将来の利用例であり、この開発で実行する指示ではありません。Sを実際に採用する40桁小文字コミットSHAに置き換えます。

```sh
python3 scripts/initial_runtime_copy.py --source-commit S
```

既定動作はdry-runです。認証付きの新側GETと、認証なしの旧側GETを行いますが、POST/PATCHは行いません。標準出力の1件のJSONを、利用者の承認した場所へ保存して計画とします。CLI自身に計画ファイルの書き込み機能はありません。

計画には固定保存先、S、新側開始コミットD0、READMEのSHA-256、6パス・サイズ・生バイトSHA-256が入ります。`plan_sha256` は計画のcanonical JSONのSHA-256です。本文やIDは含みません。日時を自動追加しないため、同じS・D0・内容なら同じ計画になります。

取得はSのtreeに記録されたblob SHAを使います。base64をバイトへ復号し、Git blob identityも確認します。すべて同じSから取得し、JSON構文、重複キー、非標準数値、キューとバッチの重複・欠損予約IDを検査します。整形・日時・本文・状態・未知フィールドを変更しません。

## 計画の承認と適用

人間が計画を確認して明示承認した後だけ、次のモードを使用します。

```sh
python3 scripts/initial_runtime_copy.py --apply-plan /trusted/plan.json --approve-plan PLAN_SHA256
```

`PLAN_SHA256` はdry-run出力の値です。dry-run出力全体、または内側のplanオブジェクトを入力にできます。計画ファイルは通常のローカルJSONとし、既存検証ツールの安全な読み取りでシンボリックリンク等を拒否します。計画の改変、保存先・パス・S・D0・ハッシュの変更は承認値不一致で停止します。承認ハッシュは署名や本人確認ではないため、計画と承認値を同時に変更できる攻撃者からは保護しません。

適用は次の順です。

1. 計画の形式、固定保存先・6パス、承認ハッシュを検証。
2. 検証CLIが対応するPOSIX/Linux環境か確認。非対応なら書き込み前に停止。
3. 新側Private確認。Sから再取得し、承認済みサイズ・ハッシュとの一致を確認。
4. 新側main=D0、READMEのみ、READMEハッシュ一致を確認。
5. 6ファイルと `snapshot-manifest.json` をGit Data APIのblob/treeへ追加。D0のREADMEを維持。
6. 親D0の単一コミットDを作成。コミットメッセージには計画ハッシュを記録。
7. Privateとmain=D0を直前に再確認し、force=falseのfast-forward更新を1回だけ要求。
8. Dを固定して全ファイル・README・manifestを再取得。`verify_snapshot.compare` で生バイト・サイズ・構造・予約IDを確認。検証前後でmain=Dも確認。

成功レポートはコミットDとパス・ハッシュ・サイズ・件数・真偽値等だけです。manifestは承認済み計画と計画ハッシュを保持し、S/D0を記録します。D自体は同じコミットへ埋め込めないため、保存後のレポートで記録します。既存検証CLIのSHAメタデータは取得元の証明ではなく、暗号署名による真正性証明も行いません。

## エラー・再実行

終了コード0はdry-run完了または適用・再検証成功、2は停止です。異常の本文やAPI応答本文、予約ID、認証値は出力しません。

- 401/403/409: 停止。権限の迂回・自動競合解消はしません。
- GETの429/5xx・通信エラー: 短い待機を入れて最大3回。復旧しなければ停止。長いレート制限では後日手動判断します。
- POST/PATCH: エラー種類にかかわらず自動再送なし。
- main更新の通信応答喪失: GETでmain=Dを確認できた場合だけ再取得検証を続行。それ以外は成否未確定として停止。
- blob/tree/commit段階の失敗: mainは更新せず停止。未参照オブジェクトが残る可能性があります。削除は行いません。
- 同じ計画の再実行: mainがD0なら再適用可能。既に計画ハッシュを持つD0直下のコミットなら、全ファイル・README・manifestを再検証して書き込みなしで成功。他のコミットは停止。
- 保存後の差分・新側の同時更新: 成功扱いせず停止。自動修復・切り戻し・旧側への書き込みは禁止。

GitHubのforce=falseはfast-forwardの保証で、一般的な原子的expected-SHAロックではありません。直前のD0照合とD0を親とする単一コミットで競合を検出しますが、他者によるforce操作等は完全に隔離できません。単独書き込み運用が必要です。

## バイト保持・プラットフォーム

APIのbase64とローカル一時ファイルのread/write_bytesだけを使用し、git checkoutやテキスト書き込みを経由しません。CRLF/LF、BOM等をそのまま保持し、git autocrlf設定の影響を受けません。ただし既存検証CLIのO_NOFOLLOW等が必要なため、適用実行はLinux/POSIXに限定します。Windowsネイティブ適用は書き込み前に停止し、WSL等の信頼するLinux環境を使用します。ネットワークマウントや敵対的なローカルファイルシステムは使用しません。

## オフラインテストと残る限界

```sh
PYTHONDONTWRITEBYTECODE=1 python3 tests/run_offline.py
```

人工データ・メモリAPI・モックHTTPのみを使い、外部通信を遮断して検証します。実在する予約本文や本番JSONを入力にしません。PR CIはこの既存ランナーを使い、既存workflow変更や手動Actions起動は不要です。

実GitHubの権限・レート制限・サービス挙動の統合検証は未実施です。GAS側の取り込み状態・投稿重複防止・自動返信OFF設定を検証するツールではありません。新側をGASや投稿処理に接続せず、旧側を唯一の本番正本として維持してください。

## API応答の安全検証

全エンドポイントの応答は、利用する必須キー・型・40桁小文字SHAを検証します。refはmainのcommit型、commitは要求したSHA・tree・親・メッセージ、treeはtruncated=false・各パス・種別・mode・SHA、blobはbase64文字列・整数サイズ・SHAを確認します。JSONのトップレベルが配列やnull、重複キー、非標準数値、欠損キー等なら固定エラーコードで停止し、応答本文やトレースバックを出しません。

blob作成応答のSHAは送信バイトから計算したGit blob SHAと一致する必要があります。tree作成応答はREADMEと6ファイル＋manifestから計算した期待Git tree SHA・直下のエントリ集合を照合し、recursive GETでも全対象を照合します。commit作成応答のtree・唯一の親D0・メッセージを確認したうえで、返されたcommitをGETして再確認してからref更新へ進みます。commit SHAの生オブジェクト再計算は行わず、型・形式と返却構造・再取得内容を照合する方式です。

POST/PATCHは不正応答でも自動再送しません。応答ボディ読み取り中の切断も通信応答喪失として扱います。PATCH後の不正応答は、mainが変更済みの可能性を残したまま停止し、自動復元しません。同一計画の再実行でのみ既存の再取得検証を行います。これらの検証追加は実GitHubの統合検証を代替するものではありません。
